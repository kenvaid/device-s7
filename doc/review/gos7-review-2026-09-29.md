## P1：优先修复

### F01 超时后保留连接，下一请求可以接受上一请求的迟到响应

位置：[tcpclient.go:153](D:/workspace/iot/edgex/gos7/tcpclient.go:153)，同文件 140–181、342–344；[telegram.go:54](D:/workspace/iot/edgex/gos7/telegram.go:54)。

`Send` 在写入失败、读取超时、EOF 或非法帧时直接返回，没有关闭/reset 会话。常规读写模板使用固定 PDU Reference；`Verify` 为空，不验证响应是否对应当前请求。请求 A 超时后发送 B，A 的迟到响应会被 B 接受。这会造成“读取成功但地址和值不对应”；写入确认也存在相同关联风险。

复现：第一次读取 DB1 字节 0，协议桩不回复，使其超时；第二次读取字节 1 时送回第一次的值 `11`，第二次返回成功并取得 `11`。连接在首次超时后仍非 nil。另有 5 个场景分别验证错误 Reference、Function、S7 Protocol ID、TPKT 版本、COTP 类型均未被拒绝。

建议：把不完整交换和协议错误视为会话失效，关闭连接并重置状态；为每个请求分配 Reference，按报文类型校验 COTP/S7 头、Reference、参数长度、数据长度和响应功能。协议身份校验不能替代超时后的会话清理，尤其在已读入半包时。

### F02 批量位写入使用不同于读取的地址单位

位置：[multi.go:49](D:/workspace/iot/edgex/gos7/multi.go:49)；读取对照为同文件 166–168。

`AGReadMulti` 对位地址编码 `Start*8+Bit`；`AGWriteMulti` 对位类型直接编码 `Start`，完全忽略 `Bit`。同一个 S7DataItem 无法表达同一位的读写。设置 `Start=10, Bit=3`，读请求编码 `000053`（83），写请求编码 `00000a`（10），会写到另一位。

建议：明确 S7DataItem 的 Start 为字节位置、Bit 为位位置，并统一读写转换及 0–7 校验。同步修改 device-s7 中把 DBX 提前折算为位地址的调用，避免修库之后发生二次乘 8。这是跨仓库契约变更，应在同一批验证中覆盖 DB、M、I、Q。

### F03 Connect 与业务操作重叠存在数据竞争，并可关闭正在使用的会话

位置：[tcpclient.go:196](D:/workspace/iot/edgex/gos7/tcpclient.go:196)、243、265；[client.go:190](D:/workspace/iot/edgex/gos7/client.go:190)，批量读写与写区域也在锁外读取 PDULength。

互斥锁只覆盖单次 Dial/Send/Close，不覆盖完整的 TCP→ISO→PDU 握手。已有 conn 时 `tcpConnect` 直接返回，但 Connect 仍重新发送 ISO 握手。ISO 验证在 Send 解锁后读取共享 LastPDUType；另一业务 Send 可把它改成 `f0`，使 Connect 误判 `errIsoConnect` 并执行 Close。PDULength 的写入及业务读取也没有同步。

复现：race detector 明确报告 `tcpclient.go:265` 写 / `client.go:190` 读，以及 `tcpclient.go:177` 写 / `tcpclient.go:243` 读。一次运行同时出现 `errIsoConnect` 和随后业务读取的 `Connection ... is null`。

建议：建立连接状态机，连接初始化及重新连接与业务交换共享明确的同步边界；同一已完成握手的会话重复 Connect 应避免重新握手。ISO 检查读取本次局部 response 的类型；PDULength 在会话发布前完成初始化，并同步访问。不要在持有同一个非重入锁的情况下调用现在会自行加锁的 Send，以免修复时引入死锁。

### F04 常规读写忽略 S7 全局错误

位置：[client.go:491](D:/workspace/iot/edgex/gos7/client.go:491)，尤其 494–503；readArea 235–239、writeArea 359–361。

`responseError` 把含 TPKT/COTP 的整个响应当成去掉传输头的 S7 PDU，读取 Data[1] 判断类型。正常 TPKT 的 Data[1] 是 0，因此函数返回 nil；若进入分支，错误码位置也不正确。单区读写只检查 item 返回码，没有补查完整响应的全局错误。

复现：带有 `Ack_Data` 全局错误 `8104` 的读、写响应，只要 item 位置为 FF，均返回成功。真实的全局错误回复若没有完整 item，还可能被错误地继续解析。

建议：统一解析传输头和 S7 头偏移，区分 Job/Ack/Ack_Data/UserData；在访问 item 前检查全局结果。成功的全局错误字段应返回 nil，不能返回非 nil 的零值 S7Error。

### F05 回复长度检查不足，截断报文可能变成零数据或触发 panic

位置：[client.go:239](D:/workspace/iot/edgex/gos7/client.go:239)、[multi.go:218](D:/workspace/iot/edgex/gos7/multi.go:218)、117–127、[control.go:94](D:/workspace/iot/edgex/gos7/control.go:94)、[block.go:85](D:/workspace/iot/edgex/gos7/block.go:85)、[datetime.go:19](D:/workspace/iot/edgex/gos7/datetime.go:19)。

单区读取只要求回复至少 25 字节，随后按请求大小读取；Send 返回 slice 的 capacity 是 2084，超出实际 length 但未超出 capacity 的切片会读到未接收的零值。批量读取把回复复制进 1024 字节 scratch，然后信任声明长度，也会把缺失部分当成零。批量写入缺少最小响应长度检查；状态、块信息、时钟的粗略长度门槛低于实际访问偏移。

复现：请求 4 字节、只返回 1 字节，单区和批量读取都返回成功，结果 `42000000`。16 字节批量写回复 panic；33 字节状态/块信息/时钟回复分别在偏移 44/42/35 panic。

建议：先验证每个字段都位于真实 len 内，再验证 item 完整性、TransportSize、声明数据长度和请求期望长度；不得把 scratch 的容量视为已收到的数据长度。所有远端报文错误应返回 error。

### F06 参数和缓冲区未验证，会崩溃或发送补零后的错误写入

位置：[multi.go:26](D:/workspace/iot/edgex/gos7/multi.go:26)、141、94；[client.go:239](D:/workspace/iot/edgex/gos7/client.go:239)、355。

批量接口只检查 itemsCount>20，没有检查 itemsCount 与 slice 长度；写入先向固定 scratch 切片，再检查是否超 PDU。读写没有在 I/O 前验证所需缓冲区长度。批量写入使用 copy，短输入不会报错，而是把剩余字节填 0 并发给 PLC。负 amount 的区域读取直接返回成功，未进行 I/O；地址、DBNumber、Amount 的窄化转换也没有可靠范围检查。

复现：空 slice/count=1 的读写 panic；Amount=1021 的批量字节写在 scratch 越界；单区读写短 buffer panic；Amount=4/Data={42} 的批量写实际发送 `42000000`，返回成功；amount=-1 的读返回 nil。

建议：在任何分配、切片、地址窄化或发送之前完成参数范围、乘法溢出、item 数量、缓冲区大小、PDU 预算检查。短写入缓冲区必须拒绝，不能隐式补零。

### F07 设置 PLC 时钟必然越界；读取时钟在网络错误时解引用 nil

位置：[datetime.go:38](D:/workspace/iot/edgex/gos7/datetime.go:38)、19；模板为 [telegram.go:141](D:/workspace/iot/edgex/gos7/telegram.go:141)。

`PGClockRead(datetime)` 实际执行写时钟。模板长度 39，但 `SetDateTimeAt(requestData,32,...)` 写 8 字节，最后访问索引 39，必然在发送前 panic。`PGClockWrite()` 实际读取时钟，在 send 返回 error/nil response 后，直接访问 response.Data，同样 panic。API 注释中的读写含义与实现、签名不一致。

复现：`clock_set_fits_template` 在索引 39 越界；`clock_get_transport_error` 对 nil response 解引用。

建议：按实际报文布局修正时间字段偏移，并首先传播 send error；补完整时钟读/写协议测试。为清晰的 Get/Set 接口提供兼容迁移方案，避免直接交换旧方法语义影响现有调用者。

## P2：功能和边界完整性

### F08 计数器写入没有进入 Timer/Counter 共用分支

位置：[multi.go:76](D:/workspace/iot/edgex/gos7/multi.go:76)、[client.go:342](D:/workspace/iot/edgex/gos7/client.go:342)。

这两处使用空的 `case s7wlcounter:` 后接 `case s7wltimer:`，Go 的 switch 不会隐式 fallthrough。批量计数器写入的 TransportSize=0、数据长度=0，完全不发送计数器数据；单区计数器写入保留默认 TransportSize=4，和采用字节长度的计数器载荷不一致。复现报文尾分别为 `00000000` 和 `000400021200`。

建议：改为一个逗号分隔的 case，并核对 CT/TM 原始 16 位数据与长度字段。

### F09 Timer/Counter 快捷接口把每个 16 位元素压成一个字节

位置：[client.go:115](D:/workspace/iot/edgex/gos7/client.go:115)、127–143、150–155。

读接口读取 amount*2 字节后，每个元素只赋给 buffer[c] 一个 byte；写接口只取 buffer[c] 一个 byte，尝试从 byte 中取得 FF00 高位永远为 0。该接口无法完整表达 Timer/Counter 的 16 位原始值。

复现：返回原始 `1234`，buffer 初始 `eeee`，AGReadTM 和 AGReadCT 都只输出 `12ee`。写 CT 的复现同时显示 `12 00`，丢失输入的第二字节。

建议：明确 []byte 接口返回/接受 amount*2 的协议字节，或新增 []uint16 接口；读写宽度、字节序及 BCD/S5TIME 解释必须统一。

### F10 SZL 分片拼接丢失前片、记录宽度倍增，返回 size 永远为 0

位置：[system.go:159](D:/workspace/iot/edgex/gos7/system.go:159)、166、171–176、180；错误判断 145。

第二片开始每次新建 slice 直接覆盖 szl.Data，没有复制已收到的前片；LengthHeader 是单条记录宽度，却每收到一片就自加翻倍；命名返回值 size 从未赋值。错误判断使用 `global!=0 && returnCode!=FF`，只坏一个条件时不会拒绝。

复现：首片 `0102`、次片 `0304`，最终 Data 为 `00000304`，记录宽度 2 变成 8，size=0；全局结果为 0 而返回码为 5 的失败回复被接受。

建议：累积 append/拷贝且保留记录头，返回有效数据总长，用 OR 判断两个独立错误条件；检查每片实际数据边界以及序列推进。

### F11 GetOrderCode 请求错误 SZL，正常成功路径必然负索引 panic

位置：[system.go:98](D:/workspace/iot/edgex/gos7/system.go:98)、101–103。

该函数请求 0131（CP 信息），而订货号应请求 0011；readSzl 返回 size=0，随后访问 Data[size-3]。即使回复中数据完全足够，正常成功路径也会在 -3 索引 panic。

复现：协议桩确认实际请求 0131；送回完整 24 字节 SZL 数据后出现索引 -3 越界。0011 的用途也与 [Snap7 的 GetOrderCode 实现](https://github.com/SCADACS/snap7/blob/master/src/core/s7_micro_client.cpp#L1859)一致。

建议：修正 ID、SZL size 返回值、版本字段和最小记录长度检查。

### F12 Read 地址语法解析不完整，合法非 DB 语法返回空成功

位置：[client.go:385](D:/workspace/iot/edgex/gos7/client.go:385)、396–419、433–456。

`MB0`、EB/EW/ED、AB/AW/AD、MW/MD 等 switch 分支为空，直接走到最终 return，结果 nil value/nil error，也不发送报文。E/A/Z 别名也存在空 case。短字符串及缺失 DBX 位段直接切片或索引，忽略 ParseInt 错误又会把错误参数转换为 0；DB/偏移按有符号 16 位解析还会限制合法范围。

复现：MB0 无 I/O 且返回 nil/nil；`D`、`DB1.X`、`DB1.DBX0` 分别 panic。Timer/Counter 分支把 nil interface 传给 GetValueAt，无法构造返回值。

建议：独立、完整的地址解析器返回结构化地址和 error；解析成功后再发请求并解码。未支持的语法应明确报错。

### F13 接受不可能的 PDU 大小，分块循环可能不推进

位置：[tcpclient.go:265](D:/workspace/iot/edgex/gos7/tcpclient.go:265)、[client.go:190](D:/workspace/iot/edgex/gos7/client.go:190)、287。

协商只拒绝 <=0，PDU=1 也会被接受；读写分块公式在过小/未初始化值下产生非正 maxElements，没有确保每次循环消耗至少一个元素。maxElements=0 且协议桩持续返回成功时，同一操作无限发送 0 元素请求，totElements 不下降。

复现：PDU=1 协商返回 nil；PDULength=18 读取 1 字节，在桩主动关闭之前连续产生 3 个零元素请求。

建议：拒绝小于协议允许范围、超过请求值或与接收能力不一致的协商结果；未完成连接时拒绝区域操作；分块前硬性要求 maxElements>0。写和 Multi 预算目前还把 7 字节 TPKT/COTP 一并算入协商 S7 PDU，需统一预算单位，避免容量边界行为不一致。

### F14 WSTRING 把 UTF-8 字节数写入字符数头

位置：[helper.go:251](D:/workspace/iot/edgex/gos7/helper.go:251)、254–265。

字符遍历使用 []rune，但长度使用 len(value)。`中文` 有 2 个字符、6 个 UTF-8 字节，结果头写 6，仅写入 2 个宽字符；读取时产生尾部 NUL 或越界。截断最大长度也按字节数判断，行为不一致。

复现：maxLen=8 时长度头为 6，回读为 `中文\x00\x00\x00\x00`。西门子 WSTRING 使用 UCS-2 字符表示，应计宽字符并校验能否编码，参见[西门子数据类型说明](https://docs.tia.siemens.cloud/r/simatic_s7_1500_et_200mp_manual_collection_enus_21/comprehensive-information/cpu-function-manuals/web-server/api-application-programming-interface/reading-and-writing-process-data/supported-data-types)。不能把超出 UCS-2 范围的 rune 直接强转 uint16。

### F15 Counter 辅助函数的位移和 BCD 算法错误

位置：[helper.go:300](D:/workspace/iot/edgex/gos7/helper.go:300)、310–311。

ToCounter 把低两位乘 256 后再送 encodeBcd，而不是编码后形成 16 位高低字节；两个 byte 加法也会先发生截断。GetCounter 对整低字节作 BCD 解码再乘 100，和三位计数器格式不匹配。

复现：`123 → 00c9 → 12900`，连库自身的编码/解码都无法往返。建议针对 0、1、99、100、123、999 和非法 BCD 建立边界验证，明确函数接受的字节序。

### F16 SetCharsAt 可能完全不修改调用方 buffer

位置：[helper.go:294](D:/workspace/iot/edgex/gos7/helper.go:294)。

函数通过 append 插入字符串，却不返回新 slice。输入 capacity 不足会重新分配，仅局部变量指向新数组；调用方保留旧数据。capacity 足够时则会插入/移动后续数据，与 Set*At 的原位写入语义不一致。

复现：`buffer="abcd"`，pos=2、value="XY"，调用之后仍然是 `abcd`，预期 `abXY`。建议按所需区间验证后使用 copy 原位覆盖。

### F17 时间/日期辅助函数偏移、精度和编码范围错误

位置：[helper.go:117](D:/workspace/iot/edgex/gos7/helper.go:117)、126、133、139、153、111、184。

- GetTODAt 忽略 pos，总读取 0；SetTODAt 丢毫秒，SetLTODAt 丢纳秒。

复现覆盖偏移、毫秒、DATE 高位、两种星期格式。范围和单位可对照[西门子数据类型](https://docs.tia.siemens.cloud/r/simatic_s7_1500_et_200mp_manual_collection_enus_21/comprehensive-information/cpu-function-manuals/web-server/api-application-programming-interface/reading-and-writing-process-data/supported-data-types)及[DTL 结构](https://docs.tia.siemens.cloud/r/en-us/v20/data-types/date-and-time/dtl-s7-1200-s7-1500)。建议统一单位和有效范围校验；Helper 底层 Set/GetValueAt 当前仅打印错误，缺少向调用方传播错误的渠道，可新增返回 error 的严格接口。

## 并发能力和使用边界

稳定的已连接 handler 内，Send 的 mutex 把每次完整请求/响应串行化，因此并发 goroutine 的单包普通读写具有基本互斥，正向协议桩测试已经通过。但**同一连接始终只有一个正在处理的请求，读写互相等待**；没有利用多 Job 的流水线来提高单连接吞吐。

不同 handler 的独立连接可以分别工作；实际 PLC 允许的连接数、通信资源、网络延迟和读写负载决定吞吐，当前审查没有进行真实设备基准。多包大范围操作与 SZL/握手不是整体串行事务，包之间可能插入其他操作；Connect、Close、超时恢复、闲置关闭还必须和业务使用协调。

其他明确限制：

- ConnectContext 的 context **仅控制 TCP Dial**，后续握手使用 Timeout，这是现有注释说明的范围；不能把它当成完整连接操作的取消期限。
- 默认 IdleTimeout=60 秒会关连接，下一次 Send 不会自动重连，调用者必须检测并重建会话。
- Close 与 Send 使用同一锁；正在阻塞的 Send 结束前，Close 无法通过关闭 socket 中断它。Timeout<=0 会没有 I/O deadline，使这类等待可能没有上界。
- Multi 最多 20 项且不自动跨 PDU 分批，只按请求长度检查不足以保证多项回复的预算；业务驱动需要设计分批策略，并检查每个 item.Error。item 级错误放在 S7DataItem.Error 中是当前 API 设计，不能只检查方法返回 error。
